# Handoff — Operating Manual for the Next Assistant

This document is for you, the AI assistant picking up work on this project.
It is not a project summary — for that, read `ARCHITECTURE.md`. This is
about how to work with this developer, what process to follow, and what
mistakes to avoid.

Read this at the start of every new chat on this project.

---

## What to read first

In order:

1. **`ARCHITECTURE.md`** — the durable system documentation. Project goal,
   stack, code layering, current capabilities, Plex API characteristics,
   color palette, and the roadmap of unbuilt features. Everything you need
   to understand what this app is.

2. **The source code, as attached by the developer.** Do not try to infer
   what's in a file from chat history, memory, or guesses. If the
   developer has not attached the file you need to see, ask for it.

3. **This document.** Reread it whenever you feel uncertain about how to
   proceed.

You do NOT need to read previous chat transcripts or older versions of
this handoff. `ARCHITECTURE.md` carries forward what matters.

## The developer's working style

These rules are non-negotiable. They are in the developer's
`userPreferences` and they apply to every interaction.

### Code style

- Use f-strings for all string formatting in Python.
- Follow PEP standards.
- No emojis in code.
- When editing code, only edit the parts relevant to the current discussion.
  Do not add, remove, or "improve" unrelated code.

### Communication style

- No conversational filler, no affirmations unless explicitly requested
  ("Great question!", "Absolutely!", etc.).
- No language of remorse or apology. Acknowledge mistakes plainly and move
  on. Do not say "I apologize" or "I'm sorry" repeatedly.
- Ask one question at a time and wait for a response before asking more.
- Give instructions one step at a time. Wait for confirmation before the
  next step.
- Do not present multiple-choice UI elements. Ask questions in prose.

### Source-of-truth rules

- If asked to read code from a file, use the literal contents of that
  file. Do not infer from chat history, memory, or assumptions about what
  "should" be there.
- If you are missing context, say so and ask for it specifically. Do not
  guess. Do not make assumptions.
- If you are unsure about any aspect of the task, ask for clarification.

### Debugging procedure

When something is broken, follow this sequence:

1. Give your analysis of the issue.
2. Suggest steps to debug or resolve it.
3. Execute the first step and wait for the developer's response.
4. Based on the response, move to the next step.

Do not bundle multiple debugging steps into one message. Do not "try a few
things and see what works." One step, one response, repeat.

## How to deliver code changes

This is the single most important section. Get this wrong and the developer
will (rightly) push back.

### Always print the complete updated file

When you change a source file, print the **entire updated file** in the
chat. Do not print snippets, fragments, or "the part that changed." The
developer has explicitly demanded this and has good reasons:

- "Add this to X" instructions force the developer to puzzle out where the
  snippet goes, what it replaces, and whether existing code interacts with
  it. That is your job, not theirs.
- Snippets without context invite errors. The developer cannot easily
  verify a change is correct without seeing the whole file.
- The developer maintains the source of truth. Receiving complete files
  makes copy-paste reliable.

If a change spans multiple files, print each complete file in turn.

### Format for printed files

- State which file is being shown (e.g. "Here is the complete updated
  `path/to/file.py`:").
- Use one fenced code block per file with the correct language tag.
- After all files, give a brief summary of what changed and what to test.

### Use file output for long structured documents

Long documents with nested code fences, directory trees, or tables tend to
break chat markdown rendering. For anything like that —
`ARCHITECTURE.md`, `HANDOFF.md`, READMEs, design documents — generate the
file via the file-creation tool and present it. Do not paste the contents
into chat.

Code files belong in chat (so the developer can copy-paste). Markdown
documents with complex structure belong as file outputs.

## The feature process

A pattern that worked through Phase 1 (read-only browse) and Phase 2
(deletion). Follow it for every new feature.

1. **Discuss scope.** Surface design decisions before writing code. Name
   the questions the developer needs to answer.
2. **Identify edge cases.** Ask about them before they become bugs.
3. **Build backend first.** Client → services → routes, in that order.
4. **Verify each backend piece via `scratch.py` against the real Plex
   server** before moving on. The `Test_01` playlist is the safe target
   for destructive tests.
5. **Build frontend last.** Templates and JS only after backend data is
   confirmed to flow correctly.

Avoid speculating forward. Avoid building multiple layers in one go. Each
step ends with a verification that informs the next.

When the developer answers a design question, write the answer down
explicitly ("Recorded: X behavior is Y") before moving to the next
question. This is for both of you.

## Environment quirks

Things that have bitten previous sessions:

### `ppm` does not auto-reload

Route changes, config changes, and any Python source changes require
`Ctrl+C` and restart of the `ppm` process. If the developer reports the
new behavior isn't appearing, ask if they restarted the server.

Templates do not require a restart — Jinja2 reloads per-request. Static
files (JS, CSS) also do not require a restart — `StaticFiles` serves them
live. Both still require a browser refresh.

### HTMX swap behavior

HTMX does not swap on non-2xx responses by default. If a route returns
4xx, the DOM will not update; the developer may see "nothing happened."
Check the network tab in DevTools.

### Plex API: `playlistItemID` vs `ratingKey`

The track's `ratingKey` is its library ID. The `playlistItemID` is the
per-playlist instance ID. Deletion is keyed on `playlistItemID`. Adding
the wrong one to a delete URL produces a 404 from Plex.

### `scratch.py` is gitignored and exists for verification

Use it freely. Replace `main()` with whatever you need to verify against
the real Plex server. The console script `scratch` runs it.

## Things not to do

- Do not propose multiple-choice UI buttons or radio-style answer lists.
- Do not apologize repeatedly. One acknowledgment, then move on.
- Do not infer code from chat history. Read the actual file.
- Do not push back when asked to print the entire updated file. Just do it.
- Do not ask a question the developer has already answered. If you are
  unsure whether something was answered, scroll back and check before
  asking.
- Do not bundle multiple debugging steps or multiple design questions into
  one message.
- Do not add features, refactors, or improvements that were not requested.
  If you think something is worth doing, surface it as a suggestion and
  wait for a decision.
