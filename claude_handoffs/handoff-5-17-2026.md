# Plex Playlist Manager — Handoff Document

A local-use web tool for editing music playlists on a Plex Media Server. Built
because the native Plex web UI presents playlists as a single flat unsorted
track list, which is unworkable for managing large playlists (the developer's
main playlist contains 6,000+ tracks).

## Project goal

Provide a cleaner interface for viewing and editing Plex music playlists,
starting with a tree view (Artist → Album → Track) and growing into a full
playlist editor with playback support.

## Scope philosophy

This is a personal tool for a single developer running against their own Plex
server on a home network. It is not designed to be:

- Multi-user or multi-tenant
- Exposed to the public internet
- Deployed to production infrastructure

Design decisions throughout favor simplicity and local-use ergonomics over
scalability and hardening.

| Server       | uvicorn                             | Standard async server for FastAPI                        |
| Templates    | Jinja2                              | Native FastAPI integration                               |
| HTTP client  | httpx (async)                       | Modern, async-capable, official Plex API consumption     |
| Config       | pydantic-settings                   | Typed config loaded from `.env`                          |
| Frontend CSS | Tailwind CSS via Play CDN           | No build step; production switch possible later          |
| Frontend JS  | HTMX 1.9.x                          | Server-rendered HTML over JSON+SPA for this use case     |
| Frontend JS  | Alpine.js 3.x                       | Client-side state (letter filtering); minimal footprint  |
| Expand/collapse | Native HTML `<details>`/`<summary>` | Zero JS for tree expansion; accessible by default       |
| Plex access  | Official Plex HTTP API              | Chosen over `plexapi` because it's the documented contract |

### Stack decisions explained

**FastAPI + Jinja2 + HTMX vs SPA:** A separate React/Vue frontend would require
a build pipeline, JSON API contracts, and client-side routing for what is
fundamentally CRUD over HTML pages. HTMX with server-rendered partials
eliminates an entire layer of complexity. The decision was reinforced by the
fact that `pyproject.toml` already committed to Jinja2 before stack discussions
began.

**Official Plex HTTP API vs `plexapi` library:** The community-maintained
`plexapi` Python library is widely used but is not officially supported by
Plex. Working against the official HTTP API directly means working against a
documented contract that's less likely to break unexpectedly, at the cost of
writing slightly more code.

**Two-layer Pydantic models:** Plex API ingestion models (`PlexPlaylistSummary`,
`PlexTrackItem`) are kept separate from domain models (`Track`, `Album`,
`Artist`, `PlaylistTree`). This isolates Plex's specific field naming
(`grandparentTitle`, `parentTitle`) from the rest of the codebase. If Plex
renames a field, only the ingestion layer changes. Tradeoff: slightly more code
upfront in exchange for cleaner separation.

## Configuration

`.env` in the project root (gitignored) contains:

```
PLEX_BASE_URL=http://<your-plex-server-ip>:32400
PLEX_TOKEN=<your-plex-token>
```

The token is retrieved by opening the Plex web app, navigating to any media
item, and inspecting the XML view URL which includes `X-Plex-Token=...` as a
query parameter. Treat the token as a password — it grants full access to the
server.

Settings are loaded via `pydantic-settings` and validated at import time
(`HttpUrl` validates the URL format).

## Phase 1: Read-only display — COMPLETE

The user can:

1. Launch the app with `ppm`
2. Navigate to `http://127.0.0.1:8765/`
3. See a sidebar listing all editable music playlists (non-smart, audio type)
4. Click any playlist to view its contents as an Artist → Album → Track tree
5. Expand/collapse artists and albums independently
6. Filter the tree to a single letter via a sticky alphabetical strip
7. Toggle back to "ALL" to see all artists

### What was built

**Plex client (`plex_client.py`):**
- `PlexClient` wraps `httpx.AsyncClient` with the `X-Plex-Token` header preset
- `get_playlists()` — fetches audio playlists, excludes smart playlists
- `get_playlist_items(playlist_id)` — fetches all items with transparent pagination
- Shared instance lifecycle via FastAPI's `lifespan` context manager

**Models (`models.py`):**
- Ingestion: `PlexPlaylistSummary`, `PlexTrackItem`
- Domain: `Track`, `Album`, `Artist`, `PlaylistTree`, `PlaylistSummary`
- `build_playlist_tree()` — groups flat tracks into nested structure
- `_bucket_letter()` — computes A-Z/# bucket for letter filtering (strips
  leading articles "the/a/an", normalizes accented characters)

**Services (`services.py`):**
- `get_playlist_summaries(client)` — slim list for the sidebar
- `get_playlist_tree(client, playlist_id)` — full tree for the main view

**Routes (`routes/playlists.py`):**
- `GET /` — landing page with playlist list
- `GET /playlists/{id}/tree` — partial template returning the tree HTML

**Templates:**
- `base.html` — shell with Tailwind, HTMX, Alpine.js CDN scripts and Plex-themed
  color palette
- `index.html` — two-column layout (sidebar + content area)
- `partials/playlist_tree.html` — tree with sticky letter strip, native
  `<details>` expand/collapse, Alpine.js letter filtering

## Key discoveries during Phase 1

These are non-obvious behaviors of the Plex API that future work must account
for:

### Smart playlists cannot be edited via API

Smart playlists are computed dynamically from filters; they have no stable
per-item IDs. The Plex API returns `playlistItemID: null` for their items,
making deletion impossible. They are excluded at the client level by filtering
on `smart == False`.

### `leafCount` vs `totalSize` discrepancy

Plex stores a playlist's reference count as `leafCount` and reports the number
of *retrievable* items as `totalSize`. These often differ. Specifically, when
files are removed from the music library, Plex does not prune the playlist's
stored references — they become orphans. The orphans count toward `leafCount`
but not `totalSize`.

For the developer's test playlist:
- `leafCount`: 6353 (stored references including orphans)
- `totalSize`: 6338 (actually playable items)

**`totalSize` is the source of truth for what we can display and edit.**
`leafCount` is misleading and is not surfaced in the UI.

### Pagination behavior

Plex's `/playlists/{id}/items` endpoint paginates large responses. Without
explicit `X-Plex-Container-Start` and `X-Plex-Container-Size` parameters, the
default response caps around 6,341 items. The client paginates with page size
500 and uses `totalSize` from the response as the loop termination signal.

Interestingly, the Plex web UI itself appears to hit the same default cap —
the developer's test playlist shows "6341 Tracks" in the official UI while the
tool's paginated client retrieves all 6338 retrievable items.

### Alphabetical bucketing rules

Following Plex's own convention:
- Leading articles ("the ", "a ", "an ") are stripped before bucketing
- Accented characters normalize to their base letter via `NFKD`
- Non-alphabetic first characters bucket to `#`
- Empty letters in the strip are rendered but disabled

## Phase 2: Editing — NOT STARTED

Goal: enable the user to remove tracks, albums, and artists from a playlist
through the tool, and have those changes persist to the Plex server.

### Anticipated work

**Backend:**
- Add `delete_playlist_item(playlist_id, playlist_item_id)` to `PlexClient` —
  wraps `DELETE /playlists/{id}/items/{item_id}`
- Add service-layer functions for batch deletion (remove all tracks for an
  artist or album in one operation)
- Add new routes:
  - `DELETE /playlists/{id}/items/{playlist_item_id}` — remove one track
  - `DELETE /playlists/{id}/albums/{album_key}` — remove all tracks in album
  - `DELETE /playlists/{id}/artists/{artist_name}` — remove all tracks by artist

**Frontend:**
- Add a remove button to each track, album, and artist node in the tree
- Use HTMX `hx-delete` to call the routes
- On success, swap the affected DOM region out (HTMX `hx-target` + `hx-swap`)
- Possibly add a confirmation step for batch removals (album/artist)

**Data integrity considerations:**
- Plex's deletion is per-`playlistItemID`. A "remove this album" action means
  iterating album tracks and issuing N delete requests, one per `playlistItemID`.
- These should run sequentially (Plex may not handle parallel mutations well)
  or in tightly-batched groups.
- After deletion, the cached tree is stale; the tree needs to refetch or the
  affected nodes need to be surgically removed from the DOM.

## Phase 3: Future features — DISCUSSED, NOT SCOPED

The following were discussed conceptually but not designed in detail. Notes
preserved here for when they're taken up.

### Adding tracks from the library

The Plex API supports `PUT /playlists/{id}/items?uri=...` for adding items. The
UX problem is **how the user finds tracks to add**, given a library with
thousands of tracks.

The developer's preferred model:

> List available artists. Click an artist to open their page, where you can
> browse their catalog (albums and tracks).

This is essentially a two-step navigation through the library:

1. **Library artist list:** flat list of all artists in the music library,
   filterable by letter (same letter-strip pattern used for the playlist tree).
2. **Artist detail page:** for one artist, show their albums (expandable to
   tracks), with "+ add to playlist" buttons at track/album/artist level.

**Why this works well:**
- Artist count in a typical library is bounded (hundreds to low thousands).
- Per-artist content is bounded (rarely >40 albums per artist).
- No lazy-loading complexity needed; each "page" fits in memory comfortably.
- Reuses the existing letter-strip filtering, color palette, and template
  patterns.

**Plex API endpoints involved:**
- `GET /library/sections` — find the Music library section ID
- `GET /library/sections/{id}/all?type=8` — all artists (type 8 = artist)
- `GET /library/metadata/{artist_id}/children` — albums for an artist
- `GET /library/metadata/{album_id}/children` — tracks in an album

**Open UX question (for the future, not yet decided):**

How does the user pick the destination playlist when clicking "+ add"?

- **A.** One-click add to a "currently selected" playlist (user selects a
  playlist in the sidebar, then everything they click "+" on goes there).
- **B.** Per-click playlist selection (a dropdown appears each time).
- **C.** A staging area / tray (items accumulate, then flush to a chosen
  playlist in one batch).

Each option implies different backend shape (single vs batch add) and template
structure. To be decided when this phase begins.

**Scope estimate:** Roughly the same complexity as Phase 1. Maybe slightly
smaller because the visual shell, color palette, letter strip, and overall
patterns are reusable.

### Playing tracks

The developer wants in-tool playback because "building a playlist demands that
you listen to music." Three implementation tiers were discussed.

#### Tier 1: Embed an HTML5 audio player in the tool

Use a library like **Plyr** (`https://plyr.io`) to wrap the browser's native
`<audio>` element with a polished player UI. Persistent player bar at the
bottom of the page, separate from HTMX-swapped content.

**What Plyr provides:** play/pause, seek, volume, time display, theming, ~30KB,
no build step.

**What still has to be solved:**

1. **Token exposure.** Audio URLs would include `X-Plex-Token=...` as a query
   parameter, leaking the server's token into the DOM, browser history, and
   logs. The fix is a streaming proxy: FastAPI route `/stream/{rating_key}`
   fetches from Plex server-side and pipes bytes to the browser via
   `StreamingResponse`. Adds complexity (byte-range requests for seeking,
   proper HTTP headers).
2. **Format compatibility.** Browsers reliably play MP3 and AAC. FLAC, ALAC,
   DSD, etc., are inconsistent. Plex's official clients handle this via
   server-side transcoding, but the transcoding API is poorly documented for
   third-party use.
3. **Persistent player across HTMX swaps.** The player needs to live outside
   the DOM regions HTMX touches, otherwise it gets destroyed when navigating
   between playlists.

**Estimated effort:** A weekend for basic, a few weekends for robust.

#### Tier 2: Plex-specific web players (libraries/embeds)

Examples like `plex-web-api`. These exist but are libraries, not drop-in
components. Plex's own web client is monolithic and can't easily be embedded.
**Not recommended.**

#### Tier 3: Remote-control an existing Plex client

Plex has a remote-control protocol. Your tool wouldn't play audio at all —
instead, it would tell an existing Plex client (Plex web app in another tab,
Plexamp desktop, phone, Roku, etc.) to play a track.

**Plex API endpoints involved:**
- `GET /clients` — list active Plex players on the network
- `GET /player/playback/playMedia?key=...&machineIdentifier=...` — play a track
- `GET /player/playback/play`, `pause`, `stop`, `seekTo`, etc. — controls

**UX shape:**
1. Tool detects available Plex players on the network.
2. User picks one as the "active player" via a dropdown.
3. Clicking a track in the tool sends a remote command to that player.
4. (Optional) Tool polls the player's state and shows current track / progress.

**Pros:**
- No streaming proxy needed.
- No transcoding/format problems (Plex client handles it).
- No token exposure in the browser.
- Leverages Plexamp's high-quality playback (gapless, replay gain, etc.) as the
  audio engine.

**Cons:**
- Requires an active Plex client somewhere on the network.
- Less immediate / inline than embedded playback.
- The control protocol has mid-quality documentation; some experimentation
  required.

**Recommendation:** Tier 3 is likely the better fit for this project's use
case. The user almost certainly has Plexamp or the Plex web app open when
working on playlists; pairing the editor with an existing player is natural,
avoids re-implementing audio plumbing, and benefits from Plex's mature
playback infrastructure.

**Fallback choice:** If embedded playback is preferred (the tool is
self-contained, no external player required), Tier 1 with Plyr + streaming
proxy is the path. Limit to MP3/AAC for simplicity.

**Decision point (not yet made):** Tier 1 (embedded) vs Tier 3 (remote
control). This is a fundamental architectural fork that shapes the entire
playback feature.

## Conventions and notes for future work

### Process for new features

The Phase 1 work followed a pattern that worked well and should continue:

1. Discuss the feature's scope and surface design decisions explicitly.
2. Identify edge cases and ask about them before writing code.
3. Build backend pieces first (client, models, services).
4. Verify each backend piece via the `scratch.py` test bed before moving on.
5. Build templates last, after backend data is confirmed to flow correctly.

Avoid building multiple layers speculatively. Each step ends with a verification
that informs the next.

### Ruff configuration

The project uses Ruff with a strict ruleset. Two notable customizations:

- `flake8-bugbear`'s `extend-immutable-calls` whitelists FastAPI's `Depends`,
  `Query`, `Path`, etc., so the framework's normal pattern of calling them in
  argument defaults doesn't trigger `B008`.
- `target-version = "py313"` matches `requires-python` in `pyproject.toml`.

### Style preferences

The developer's preferences for working in chat with an AI assistant (captured
in their `userPreferences`) include:
- f-strings for all string formatting
- One step at a time, wait for response before continuing
- One question at a time, wait for response
- Don't infer code from chat history; always use literal sources
- Only edit code parts relevant to the discussion
- No multiple-choice question UI elements; ask questions in prose
- No emojis in code
- Debugging proceeds: analysis → propose steps → one step at a time

These preferences apply to any future AI-assisted work on this project and
should be respected.
